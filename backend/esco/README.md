# ESCO source

Prepares [ESCO](https://esco.ec.europa.eu/) (the European Commission's
classification of occupations and skills) as an incoming source for the
taxonomy pipeline. It is the second external source after O*NET (`../onet/`),
added to test whether matching tuned on SkillsFuture generalises; the
results are in `../taxonomy_pipeline/docs/generalization-findings.md`.

Unlike O*NET, ESCO is published as separate files linked by concept URI, so
`flatten_esco.py` joins them into one table first. After that the source goes
through `taxonomy-pipeline import-source` like any other (see "Next round" in
`../taxonomy_pipeline/README.md`).

## Layout

```text
esco/
├── raw/                     # the downloaded ESCO CSVs and the flattened join (gitignored, see below)
├── flatten_esco.py          # joins occupations + skills + relations into raw/esco_flat.csv (tested in
│                            #   ../taxonomy_pipeline/tests/test_flatten_esco.py, linted in its CI job)
├── esco_mapping.yaml        # import-source mapping: which column is category / speciality / tag, essential-only filter
├── isco_major_groups.csv    # ISCO-08 major-group labels, for the category derived from the code
├── esco_taxonomy.sql        # generated by import-source: esco_categories / _specialities / _tags / _speciality_tags
└── esco_tag_context.json    # generated by import-source: each tag's description, for Case B
```

## Getting the data

On [esco.ec.europa.eu/en/use-esco/download](https://esco.ec.europa.eu/en/use-esco/download),
choose version v1.2.1, content "classification", language English, format
CSV. The site emails a download link. Copy these files from the zip into `raw/`:

| File | Columns the script reads |
|---|---|
| `occupations_en.csv` | `conceptUri`, `preferredLabel`, `iscoGroup` (4-digit ISCO-08 unit group) |
| `skills_en.csv` | `conceptUri`, `preferredLabel`, and `description` if present |
| `occupationSkillRelations_en.csv` | `occupationUri`, `skillUri`, and `relationType` if present |

Other columns are ignored. ESCO is published by the European Commission under
its reuse policy (CC BY 4.0); credit "ESCO" if you redistribute derived data.

The committed `esco_taxonomy.sql` was generated from a trimmed copy of the
v1.2.1 export. The trimmed copy kept only the columns above (without
`description`) and only `essential` relations. Its relations file therefore
has no `relationType` column, so it was flattened with
`--assume-relation-type essential`. That copy is why `esco_tag_context.json`
holds no descriptions. A full download hasn't been run through the script. It
should give the same links plus descriptions, unless its repeated rows differ
in `description` (see below).

## Mapping onto the taxonomy

| Taxonomy level | ESCO | Example |
|---|---|---|
| service | fixed: Function (id 2), set in `esco_mapping.yaml` | Function |
| category | ISCO-08 major group: the unit group's first digit, named from `isco_major_groups.csv` | Professionals |
| speciality | occupation (`preferredLabel`) | technical director |
| tag | skill or competence (`preferredLabel`) | manage musical staff |
| tag description | skill `description`, when the export has it | |

ESCO marks each occupation-skill link `essential` or `optional`. The script
keeps every link and writes its type to `relation_type`. The mapping's
`filters: {relation_type: essential}` decides that only essential links are
imported, because essential is the closer match to "this occupation's tags".
Change the filter to `[essential, optional]` to import both, without rerunning
the script. A skill that no kept link uses is not imported, because the flat
table has one row per link.

That gives 10 categories, 3,039 occupations, 11,378 skills and 67,600 links.
That is about 65 times O*NET's hot-technology slice, so the judge and Case B
cost of a full ESCO round scales accordingly. Add a `filters` block to the
mapping (for example on an extra column you keep in the flatten output) before
running a paid round.

The flat table's columns are `isco_group, occupation, skill,
skill_description, relation_type`.

ESCO v1.2.1 repeats some occupation and skill rows. In the trimmed copy, 4
occupation rows and 21 skill rows repeat with identical values. The script
compares only the columns it uses (the table above, including `description`
when present). A repeat whose values there match is dropped. A repeat whose
values differ stops the script with both rows' line numbers, because the join
would have to guess which row is right. A repeat that differs only in a column
the script ignores (e.g. `altLabels`) is dropped and counted separately in the
summary. The same link listed twice with different relation types also stops
the script.

## Running it

From `backend/esco/`, then `backend/taxonomy_pipeline/` with the pipeline installed:

```bash
python flatten_esco.py                       # writes raw/esco_flat.csv, prints what it dropped
# a relations file without relationType (like the trimmed copy) needs:
#   python flatten_esco.py --assume-relation-type essential
cd ../taxonomy_pipeline
taxonomy-pipeline import-source --mapping ../esco/esco_mapping.yaml \
    --baseline-snapshot integrations/<previous-round>   # optional: also write the round config
```

`import-source` writes `esco_taxonomy.sql` and `esco_tag_context.json` next to
the mapping and prints the round's next commands. To reproduce the
generalisation numbers, run `taxonomy-pipeline run --config
configs/generalization_v1.yaml`.
